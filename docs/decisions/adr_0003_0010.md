# ADR-0003 — CLI-first presentation, FastAPI deferred
# ====================================================
#
# Status: ACCEPTED
#
# Context:
# The architecture lists FastAPI as a potential API layer, but there is no
# real HTTP consumer yet.
#
# Decision:
# Implement the CLI as the canonical interface. Defer FastAPI until a real
# consumer requires it. If FastAPI is introduced later, the API must not
# bypass domain validation, risk, or execution contracts.
#
# Consequences:
# - No unnecessary HTTP surface area early.
# - API remains possible later without retrofitting domain logic.
#

# ADR-0005 — Signal/fill timing convention
# =========================================
#
# Status: ACCEPTED
#
# Context:
# The architecture requires an explicit signal/fill timing convention to avoid
# look-ahead ambiguity (spec §17, §9).
#
# Decision:
# Default convention:
# - Signal decision at bar close at timestamp T
# - Execution/fill at next-bar open at T+1
#
# This convention is locked with tests and documented. Any deviation requires
# an ADR.
#
# Consequences:
# - No silent perfect fills.
# - Deterministic, testable execution semantics.
# - Any alternative timing model must be explicit and justified.
#
#
# ADR-0006 — Numerical tolerance policy
# ======================================
#
# Status: ACCEPTED
#
# Context:
# Floating-point calculations make exact equality unrealistic for many
# financial metrics.
#
# Decision:
# - Byte-identical artifacts are enforced where required.
# - Floating-point comparisons use documented tolerances.
# - Tolerances are declared explicitly and tested.
#
# Consequences:
# - Reproducibility is defined precisely rather than hand-waved.
# - Tests must state the tolerance they use.
#
#
# ADR-0007 — P01 contract fixtures and boundaries
# ===============================================
#
# Status: ACCEPTED
#
# Context:
# P01 may not be available as a real system during early P02 development.
# P02 must not reimplement P01.
#
# Decision:
# Define an explicit P01 contract, implement deterministic P01-compatible
# fixtures for early development/testing, and clearly label fixtures as
# fixtures. The real-P01 integration boundary is documented and tested as a
# contract.
#
# Consequences:
# - Early development is not blocked by P01 availability.
# - The boundary is explicit and testable.
# - Fixtures are not represented as real P01 production data.
#
#
# ADR-0008 — Deterministic experiment rerun policy
# ===============================================
#
# Status: ACCEPTED
#
# Context:
# Reproducibility is a core requirement (NFR-001, spec §26).
#
# Decision:
# Experiments store resolved configuration, dataset identity, code commit,
# environment, and seed. Reproduction reruns the experiment and compares
# outputs using declared tolerances or byte identity where appropriate.
#
# Consequences:
# - Reproduction failures are visible and actionable.
# - Experiments are auditable and rerunnable.
#
#
# ADR-0009 — Toolchain selection
# ==============================
#
# Status: ACCEPTED
#
# Context:
# We need a small, stable, fast toolchain for formatting, linting, type
# checking, and testing.
#
# Decision:
# - Ruff for formatting + linting
# - mypy (strict) for static typing
# - pytest for testing
# - bandit + pip-audit for security
#
# Consequences:
# - Fast local feedback.
# - CI mirrors local toolchain.
#
#
# ADR-0010 — Docker usage and scope
# ==================================
#
# Status: ACCEPTED
#
# Context:
# The architecture requires a reproducible containerized environment but does
# not require Docker to be the only way to run the project.
#
# Decision:
# Provide Dockerfile + .dockerignore for fresh-environment verification and CI.
# Local development remains practical without Docker.
#
# Consequences:
# - Fresh-environment verification is possible.
# - Docker is not a development choke point.
